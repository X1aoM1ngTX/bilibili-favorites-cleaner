# B站收藏夹清理工具 — 技术选型

## 1. 各版本技术栈回顾

| 版本 | 前端 | 后端 | 部署方式 | 结果 |
|------|------|------|----------|------|
| old | 原生 HTML/JS/CSS | Node.js + Express | Web（单服务） | 功能不足，放弃 |
| new | Vue 3 + Ant Design Vue + Pinia | Node.js + Express | Web（双服务） | 部署复杂，放弃 |
| app | Vue 3 + Ant Design Vue + Pinia | Rust (Tauri) | 桌面应用 | 维护成本高，放弃 |
| nextjs | React 19 + Tailwind CSS + Zustand | Next.js API Routes | Web（单服务） | 功能未完整，中断 |

### 历史教训

1. **双服务部署是失败模式**：new 版本需要同时启动前后端，用户体验差
2. **Rust 对本项目是过度设计**：Tauri 版本的 Rust 后端只做 HTTP 代理，杀鸡用牛刀
3. **功能完整度 > 技术新颖度**：多次因追求新技术而未完成功能
4. **API 代理层不可避免**：B站 API 需要服务端代理以添加正确的请求头和避免 CORS

## 2. 候选方案对比

### 方案 A：Next.js 全栈（推荐）

**架构**：Next.js App Router，前端 + API Routes 一体化

| 维度 | 评价 |
|------|------|
| 开发效率 | ★★★★★ — 一个项目搞定前后端，API Routes 消除跨域问题 |
| 部署简便 | ★★★★★ — `next build && next start` 或 Vercel 一键部署 |
| 类型安全 | ★★★★★ — 全栈 TypeScript，API 类型共享 |
| 生态成熟 | ★★★★★ — React 生态最大，组件库丰富 |
| 维护成本 | ★★★★☆ — 技术栈主流，易于找到参考和贡献者 |
| 桌面支持 | ★★☆☆☆ — 无原生桌面体验（但可用 Tauri 包装） |

**适合场景**：Web 优先，快速交付，后续可扩展为桌面应用

### 方案 B：Tauri 桌面应用

**架构**：Tauri 2 + Web 前端 + Rust 后端

| 维度 | 评价 |
|------|------|
| 开发效率 | ★★☆☆☆ — 需维护 Rust 后端 + Web 前端两套代码 |
| 部署简便 | ★★★☆☆ — 需编译为各平台安装包 |
| 类型安全 | ★★★☆☆ — 前后端类型不共享（Rust ↔ TypeScript） |
| 生态成熟 | ★★★☆☆ — Tauri 生态在成长中，但不如 Web 生态 |
| 维护成本 | ★★☆☆☆ — Rust 后端问题排查困难 |
| 桌面支持 | ★★★★★ — 原生桌面体验，离线可用 |

**适合场景**：明确需要桌面应用、离线使用、对安装包体积敏感

### 方案 C：Electron 桌面应用

**架构**：Electron + Web 前端 + Node.js 后端

| 维度 | 评价 |
|------|------|
| 开发效率 | ★★★★☆ — 纯 JS/TS 技术栈 |
| 部署简便 | ★★★☆☆ — 需编译，安装包大（100MB+） |
| 类型安全 | ★★★★☆ — 可全 TypeScript |
| 生态成熟 | ★★★★★ — 最成熟的桌面应用方案 |
| 维护成本 | ★★★☆☆ — 安装包大、内存占用高 |
| 桌面支持 | ★★★★★ — 原生桌面体验 |

**适合场景**：需要桌面应用但不想学 Rust，对安装包体积不敏感

### 方案 D：纯前端 + Serverless 函数

**架构**：Vite/React SPA + Cloudflare Workers / Vercel Edge Functions

| 维度 | 评价 |
|------|------|
| 开发效率 | ★★★★☆ — 前端为主，API 层轻量 |
| 部署简便 | ★★★★★ — 全球 CDN，零运维 |
| 类型安全 | ★★★★☆ — TypeScript |
| 生态成熟 | ★★★★☆ — 快速发展中 |
| 维护成本 | ★★★★☆ — 无服务器 |
| 安全性 | ★★☆☆☆ — Cookie 通过用户浏览器传递到 B站，有暴露风险 |

**适合场景**：追求极致部署简便，用户信任度高

## 3. 推荐选型

### 推荐：Next.js 全栈方案

**理由**：

1. **历史验证**：nextjs 版本已实现大部分功能，证明该方案可行
2. **架构简洁**：API Routes 统一前后端，无需维护独立后端服务
3. **部署灵活**：可部署到 Vercel（零配置）、Docker、或任何 Node.js 服务器
4. **团队友好**：TypeScript + React 是最主流的前端技术栈，学习资料丰富
5. **可扩展**：未来如需桌面版，可用 Tauri 包装（已有成功先例）

### 具体技术栈推荐

| 层次 | 选择 | 理由 |
|------|------|------|
| **框架** | Next.js (App Router) | 全栈统一，API Routes，SSR/SSG 灵活 |
| **语言** | TypeScript | 类型安全，减少运行时错误 |
| **前端库** | React 19 | 生态最大，社区活跃 |
| **UI 组件库** | shadcn/ui + Tailwind CSS | 可定制、不臃肿、现代设计 |
| **状态管理** | Zustand | 轻量（~1KB），API 简洁，支持持久化 |
| **HTTP 客户端** | 内置 fetch（服务端）+ ky（客户端） | 减少依赖，ky 是 fetch 的轻量封装 |
| **拖拽排序** | @dnd-kit/core | React 生态最成熟的拖拽库，无障碍支持好 |
| **图标** | Lucide React | 轻量、一致、tree-shakable |
| **部署** | Vercel / Docker | 开发用 Vercel 零配置；自部署用 Docker |

### 不推荐的选型

| 技术 | 原因 |
|------|------|
| Ant Design Vue | Vue 生态，与 React 不兼容 |
| Vuetify / MUI | 设计风格固定，定制成本高 |
| Redux | 模板代码多，对项目规模来说过重 |
| Axios | 服务端用 fetch 足够，无需额外依赖 |
| Tauri（作为首选） | Rust 后端对本项目是过度设计 |

## 4. 关键技术决策

### 4.1 Cookie 安全存储

**问题**：用户的 B站 Cookie 包含敏感信息（SESSDATA），需要安全存储。

**方案**：

| 方案 | 优点 | 缺点 | 推荐 |
|------|------|------|------|
| localStorage | 简单、无服务端依赖 | XSS 可窃取 | ✅ 适用本项目 |
| HttpOnly Cookie | 防 XSS | 需要后端配合 | 不必要 |
| 服务端 Session | 最安全 | 需要数据库 | 过度设计 |

**结论**：本项目用户是自己的 Cookie 管理者，使用 localStorage + Zustand persist 即可。Cookie 仅在 API Routes 服务端使用，不会发送到第三方。

### 4.2 API 代理方案

**问题**：前端不能直接调用 B站 API（CORS 限制），需要服务端代理。

**方案**：使用 Next.js API Routes 作为代理层

```
浏览器 → Next.js API Route → B站 API
         (添加请求头)          (返回数据)
```

**优势**：
- Cookie 和 CSRF token 仅在服务端使用，不暴露给前端
- 统一管理请求头（User-Agent、Referer、Origin）
- 统一错误处理和频率控制
- 前端只需调用本地 API

### 4.3 拖拽排序实现

**方案对比**：

| 库 | 优势 | 劣势 |
|----|------|------|
| @dnd-kit/core | React 原生、无障碍支持、灵活 | 需自己实现列表排序逻辑 |
| react-beautiful-dnd | API 友好、动画好 | 已停止维护 |
| dnd-react-sortable | 简单易用 | 社区较小 |
| 原生 HTML5 Drag & Drop | 零依赖 | 移动端不支持，实现复杂 |

**结论**：使用 `@dnd-kit/core` + `@dnd-kit/sortable`，React 生态首选，支持触摸设备。

## 7. 风险与对策

| 风险 | 影响 | 对策 |
|------|------|------|
| B站 API 变更 | 功能失效 | 封装 API 层，变更时只改一处 |
| Cookie 安全 | 账号风险 | Cookie 仅服务端使用，不发送到第三方 |
| 频率限制 | 操作失败 | 添加请求间隔控制和重试机制 |
| QR码登录不稳定 | 登录体验差 | 优先支持手动 Cookie，QR码作为增强功能 |
| 技术栈升级 | 维护负担 | 锁定主版本，按需升级 |
